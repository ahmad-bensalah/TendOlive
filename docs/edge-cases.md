# Edge cases: test suite and results

CSTAM 3.0 criterion **Edge Case & Data Validation Handling**: graceful handling of incomplete tender specifications, noisy
web research data and missing internal references. This page is the suite, its execution result and the gaps it found.

## Run it

```bash
node test/edge_cases.js
```

Plain Node (18+), no dependency, no n8n, no model, no network; runs in under a second. `node test/edge_cases.js --md` also
prints the results table below. Exit code 0 = every case passes or is a listed known gap; 1 = an unexpected failure.

## How it works

- **The current built code.** Each case takes the `jsCode` of a node from `dist/RFP - Main.json` and runs it with a stubbed
  `$` / `$input` (the same way `test/replay.js` does), so it tests exactly what you import into n8n. After editing `src/`,
  run `node build.js` first.
- **One case per edge case.** A small hand-made input in the shape the upstream node really produces (a tender page and the
  extract LLM's answer, an analysis answer, an agent answer with its tool calls, a RAG answer...), an expected handling, and
  PASS / FAIL. Cases marked *(real)* use inputs recorded in the n8n run of 2026-10-19 (`qwen3:4b-instruct`, saved pages):
  the cut dates "November 9," and "٢٦ أكتوبر ٢", the "AVIS RECTIFICATIF" page, the olive-sale analysis, the scout run
  home → menu → list, the research of EPA-SHOM and RESAH, the RESAH market study. They are kept, trimmed, in
  `test/edge_cases_fixtures.json` so a new run in `test/out/` cannot change them.
- **"Today" is fixed** to 2026-10-19 (the day of that run), so expiry and days left are stable.
- **Known gaps.** A case always states the right handling. If the code does not do it, the case carries its code location
  and is reported `KNOWN GAP` (it does not fail the run); when a fix makes it pass, the suite prints `FIXED?` so the entry
  is moved to the fixed list below. The four gaps the suite found first were fixed on 2026-10-20 (below).
- **The suite catches regressions.** Checked by running it on deliberately broken copies of node code: Clean no longer
  drops award notices, Join RAG no longer counts requirements the RAG did not return (2 cases turn `FAIL`, exit code 1);
  and each 2026-10-20 fix undone in turn (the type check before the quote check, an empty RAG answer read as "nothing
  covered", the first word of a sentence not checked in Parse Research or Parse Market, no key partners, every award taken
  as the buyer's, a dropped CPV without warning): each turns its own case `FAIL`. So does each fix of the review that
  followed (the kind of body dropped from the buyer name, the SIREN rule, every first word checked or only by its shape,
  the possessive "'s" read as a word, a multi-winner award made IT for all its winners, a copy that proves IT left out).

## Gaps found by this suite, fixed on 2026-10-20

1. **An unknown `tender_type` skipped the quote check** (case 102) — `src/main/AN2_verify_analysis.js`. `else if
   (!v.tender_type)` came before the quote check, so an answer with a type not in the list ("cloud_migration", fit high, an
   invented quote) kept fit `high`: the tender was researched and sent to the RAG and the proposal service on the model's word
   alone. Now the type check and the quote check run apart: the type becomes "other" (`tender_type_invalid`) and the quote is
   still checked (`quote_not_in_text` / `quote_missing`, fit one level down); with the tender's real quote the fit stays.
2. **An empty RAG answer read as "nothing covered"** (case 159) — `src/main/RG2_join_rag.js`. The requirements the RAG did not
   return were added to the matrix before the empty-matrix test, so "RAG returned an empty matrix" never fired and Build
   Proposal Input recommended `no_bid`. Now an answer with no matrix row (HTTP 200 with `{}` or an empty matrix) is a RAG
   fault: `rag.status` error with that warning (the RAG's own warnings kept), so the proposal input says `review` (coverage
   unknown, the reason names the fault) and Run Summary counts a failed RAG call.
3. **Invented organisation as the first word of a summary sentence** (case 53) — `src/main/BU2_parse_research.js`.
4. **Invented competitor as the first word of a positioning sentence** (case 186) — `src/main/MK2_parse_market.js`.
   Both name checks looked only at capitalised words that are not the first of their sentence, so "Capgemini runs the city IT
   systems." / "Capgemini usually wins these contracts." stayed. Now the first word is checked when it reads as a name: by
   its shape (a capital, "&" or "." after its first letter: "SOPRA", "OliveSoft", "BLUEDROP.FR"), or as the subject of a
   supplier's claim (it wins, runs, hosts, supplies, quoted..., "is the incumbent", "remporte", "gère"), and never when it is
   a word sentences start with (the agents' own openers in the recorded runs, "The", "Its", "Bids", "Expect"..., and words
   with an English ending, "Recently", "Typically"). A first version checked every first word that is no listed opener: the
   review found it removed true sentences a new wording starts with, advice ("Leverage ...", "Stress hosting in France."),
   adjectives ("Strong references matter.", "Medium-sized local authority ..."), French ("Située à ...", "L'acheteur ...") and
   "OliveSoft's ..." (the possessive read as a word "s", also inside a sentence). Those are controls of cases 53 and 186 now.
   The buyer's own name passes as before, being in the evidence. The code before the fix, its first version and this one
   give the same summaries and positionings on the 30 research answers and 21 market answers recorded in `test/out`. Left
   as is: an invented name that is the subject of no such claim ("Atos, as always, ...") or ends like an English word
   ("Boeing wins ...") still passes as the first word.

Also fixed (case 13): an unprovable CPV or estimated value was dropped without a warning; now `cpv_not_in_text` /
`estimated_value_not_in_text`, like the buyer and the contacts (a "N/A" value, without a digit, is dropped silently).

Smaller observations (not counted as gaps): when one tool call reports two API errors only the first is kept in the market
checks (case 183 lists the TED 503, not the DECP timeout); an agent answer with an empty `summary` is invalid as a whole, so
its `buyer_type` falls back to `unknown` (strict, but safe).

## Key partners (prospect research, 2026-10-20)

`buyer_profile.key_partners` was always `[]`. Build Proposal Input now fills it with the suppliers that won **this buyer's own**
contracts, and nothing else (cases 220 to 223):

- **Where from.** The buyer's BOAMP award notices (Parse Research keeps the notice ids behind each past winner, and all the
  winners each notice names) and its awarded contracts seen by the market study (Parse Market's new `market.buyer_awards`: a
  DECP row read by the buyer's SIREN, or a DECP / TED / TUNEPS row whose buyer name is the notice's or the registry's, the
  legal form aside: "GIP RESAH" ~ "RESAH", "Epa Shom" ~ "EPA-SHOM"; "Testville Habitat" is not "Ville de Testville"). The
  kind of body is part of the name, its synonyms made one as the buyer_awards tool does ("COMMUNE DE LYON" = "Ville de
  Lyon", "Conseil départemental du Rhône" = "Département du Rhône"): the review found that dropping it made the Métropole de
  Lyon, the Centre hospitalier de Cholet or the Département de la Guadeloupe the same buyer as the Ville de Lyon, the Ville
  de Cholet and the Région Guadeloupe, so a comparable contract of theirs made its winner a partner (case 222). With the
  buyer's SIREN known, a DECP row counts only when read by that SIREN: DECP prints no SIREN on a row and namesakes exist
  (two COMMUNE DE SAINT-DENIS). RESAH's study loses 13 comparable DECP rows named like it that way; its 20 newest own awards
  still come from the SIREN call and TED. The comparable contracts of other buyers never make a partner.
- **Shape.** `key_partners` = the names, a list of strings (what the studio's examples and the CSTAM UI read);
  `key_partners_detail` = `{name, relation, awards, last_award, evidence[]}`, relation "past IT / digital supplier" (listed
  first) or "past supplier"; evidence = up to 3 awards `{source, id, date, title, amount, currency, url}` (BOAMP and TED with
  their notice URL). One per company ("SOPRA STERIA S.A." = "SOPRA STERIA"), one award published in BOAMP and TED counted
  once, at most 8 partners. No award found: both empty.
- **IT relation.** An award proves IT work (software, data, web... in its title, or a CPV 72 / 48) for a winner it names
  alone; one naming several winners (lots, co-contractors) only when it is about IT alone, no CPV outside 72 / 48 ("AOO AMOA
  SI": 6 consultancies). The review found that RESAH's TED T703576-2026 (CPV 38900000 + 48180000) made the 3 vendors it
  names (MORGATE BIOMEDICAL, GAMIDA, DIMOMAINT, medical equipment) IT suppliers, ranked first, through its BOAMP copy
  26-97793, while the 3 software makers of that 6-winner notice were not: who won the software lot is not said, so none of
  them is now (case 223). A copy of the award that proves it for one winner (its lot alone, CPV 48) is listed in the evidence.
- **Hand-off.** Adapt for Studio passes both unchanged; the studio's own normaliser keeps `buyer_profile` as it is (checked
  in `test/studio_adapter.test.js`).
- **On the recorded runs.** EPA-SHOM: BLUEDROP.FR, NORGAY, WORLDLINE, OPEN, COEXYA (its TED awards) then 3 non-IT suppliers
  of its BOAMP notices; RESAH: 8 "past supplier" (lab and test-equipment vendors) of its 20 own awards, none shown as IT;
  Ministère de l'Intérieur: the 6 consultancies of "AOO AMOA SI" first; Métropole européenne de Lille: 8 IT suppliers
  (market study only, not researched); OPPIC: the non-IT winners of its BOAMP notices (the market tools found no contract of
  its own); City'up: none (no award notice nor contract of its own found).

## Where the other tests fit

`node test/edge_cases.js` checks one node at a time on edge inputs. `node test/replay.js <execution.json>` replays a whole
recorded run through the current code; `test/e2e.js` runs the whole workflow in a throwaway n8n container (README);
`node test/studio_adapter.test.js` runs `Adapt for Studio` and then the proposal studio's own normaliser on the 10 real
proposal inputs of run 3 (what a deck would show, before and after the adapter).

To add a case: one `C(area, case, input, expected, node, async ok => { ...; return 'what happened' }, gap?)` call in
`test/edge_cases.js`; the builders above the cases make the usual inputs (`page`, `extractAnswer`, `tender`, `analysisAnswer`,
`buyer`, `step`, `researchAgent`, `ragTender`, `ragAnswer`, `marketTask`, `award`, `marketAgent`).
